# Conventions

How this codebase is written, and why. The point is consistency: a reader
should not be able to tell which file was written when.

Run `just check` before pushing. It formats, lints, tests, verifies the
Rust↔Swift bridge, and drives the real app end to end.

## Rust

### Lints

The policy lives in `[workspace.lints]` at the repo root and every crate
inherits it with `lints.workspace = true`. Prefer changing it there over
sprinkling `#![allow]` through source files.

The `rust` group follows [tokio's][tokio-lints]: `missing_docs`,
`missing_debug_implementations`, `unreachable_pub`, `unused_must_use`, and
`rust_2018_idioms`. `unsafe_code` is `forbid` — nothing here needs it, and the
FFI layer is generated rather than hand-written.

`clippy::pedantic` runs at `warn`. Two additions borrowed from [axum][axum-lints]:
`print_stdout` and `dbg_macro`, because a relay and a crypto core have no
business writing to stdout. Logging goes through `tracing`.

**The build is warning-clean. Keep it that way.** An `#[allow]` needs a comment
saying why; the one in `ffi.rs` is the model — UniFFI dictates by-value
arguments, so `needless_pass_by_value` cannot be satisfied there.

`clippy.toml` lists proper nouns (OpenConv, UniFFI, Keychain, SQLite) that
`doc_markdown` would otherwise want in backticks. Backticks mean *this is
code*; product names are not code. Real identifiers — `KeyPackage`, `Welcome`,
`MemoryStorage` — do get backticks.

### Errors

Libraries define a `thiserror` enum with one variant per failure mode; binaries
may use `anyhow`-style opaque errors. Variants carry structured data, not
formatted strings, *except* at boundaries: `Error::Mls(String)` deliberately
flattens openmls errors so its types never leak through the FFI, and
`ffi::ClientError` flattens further still for the same reason.

Every public fallible function documents a `# Errors` section. This is
[C-FAILURE][api-guidelines] and clippy enforces it.

Never `unwrap()` or `expect()` in library code. Binaries may, at startup, where
a failure should be loud and immediate. `Client::lock` is the exception that
proves the rule: a poisoned mutex means group state is untrustworthy, and
continuing would be worse than panicking.

### Secrets and `Debug`

**Types holding key material implement `Debug` by hand and redact.** `Member`,
`Vault`, `Provider`, and `Snapshot` all do. A derived `Debug` would print
identity keys and ratchet state into any log line or panic message that
formats one. Use `finish_non_exhaustive()` so the omission is visible.

This is not a style preference. It is the difference between a log file being
boring and being a key compromise.

### Naming

Follow the [API Guidelines][api-guidelines]: `as_` for borrowed conversions,
`to_` for expensive ones, `into_` for consuming ones; constructors are
inherent statics; getters drop the `get_` prefix.

### Documentation

Every public item is documented — `missing_docs` enforces it. Module headers
explain *why the module exists*, not what its functions are called.

Comments explain decisions, not mechanics. The good ones in this codebase say
what was tried, what broke, and what the real fix would be: see the
`OPENCONV_DATA_DIR` comment in `store.rs`, which records a Keychain ACL
failure that cost an hour.

## Swift

`swift format` ships with the toolchain; config is `clients/macos/.swift-format`,
set to a 100-column limit so both languages agree.

**Generated bindings are never formatted or linted.**
`Sources/OpenConvCore/openconv_core.swift` and the `openconv_coreFFI` headers
are UniFFI output, regenerated by `scripts/gen-bindings.sh` and gitignored.
Only `Sources/OpenConv` and `Sources/BridgeCheck` are ours.

Rules worth calling out, all enforced: no force-unwrapping, no implicitly
unwrapped optionals, lowerCamelCase, ordered imports, early exits via `guard`.

UI state is `@MainActor` and mutated only there — `ChatModel` is the model.
Errors from the Rust core arrive as thrown Swift errors; surface them in the
UI rather than swallowing them.

## Product rules

These outrank style, and apply in both languages.

**The relay stays blind.** `crates/server` has no code path that parses,
decrypts, or inspects a payload. It moves opaque bytes. Every feature that
wants the server to understand a message is a feature that breaks the privacy
claim — find another way.

Ordering is the one exception, and it is deliberately shaped to stay blind:
the relay stamps a sequence number on every frame without looking past it, and
clients do the work of deciding what that ordering means. Commit conflict
resolution lives in `Member::receive`, not in the server. Serialising commits
by having the relay recognise them would have been simpler and would have cost
the privacy claim.

**Protocol definitions live in Rust, once.** Frame tags are `FrameKind` in
`openconv-core`, exported through UniFFI. Swift does not get its own copy.
Two definitions drift; this one nearly did.

**Never destroy key state on a decryption failure.** A MAC failure is exactly
the signal an attacker would use to knock a client out of a session.
`Member::receive` returns an error and leaves group state untouched.

**Validate anything off the network before trusting it.** `add_member` runs
`KeyPackageIn::validate` rather than accepting the deserialised form.

## Dependencies

`cargo deny check` runs in CI and locally via `just deny`. It gates licences,
advisories, wildcard versions, and registries. Anything not on the allow list
in `deny.toml` fails the build, so adding a licence there is a decision about
what the project may ship and should be argued in the PR.

**One obligation worth knowing before you touch them.** UniFFI and hpke-rs are
MPL-2.0 — weak, file-level copyleft — and both are load-bearing: UniFFI is the
Rust↔Swift bridge, hpke-rs comes in through openmls. Linking them into this
MIT work is fine and the combined product still ships as MIT.

What is not fine is forking or vendoring either one in-tree and modifying it
without publishing those changes under MPL-2.0. Consuming them from crates.io
keeps this a non-issue; vendoring is what turns it into an obligation.

## Tests

Group-protocol behaviour is tested with **at least three members**. Two
members cannot expose commit fan-out or concurrent-commit bugs — both of which
were live in this codebase and invisible to every two-member test.

Test the negative for security properties. `wire_bytes_do_not_contain_plaintext`
fails if encryption silently no-ops; every "can Bob read it?" test still passes
in that case.

**A test earns its place by failing when the thing it names is broken.** The
cheapest way to find out is to break that thing on purpose and check which
tests go red. Three worth keeping honest: make `persist` a no-op, stop a
losing member clearing its staged commit, and write the vault unencrypted.
Each should take tests with it.

When doing that, assert the mutation actually applied. A patch that silently
fails to match looks exactly like a test gap, and will send you hunting for
coverage you already have.

Assertions should be precise about what they expect. `matches!(x, Ok(_) |
Err(_))` passes no matter what happens; find out what the real behaviour is
and assert that.

Prefer deleting a test to keeping one that cannot fail. Tests that hand-deliver
the thing under test are a common trap: a test that passes the commit to a
member by hand proves openmls can apply commits, not that this codebase ever
sends one.

`BridgeCheck` is a plain executable, not a test target, because XCTest and
swift-testing both require a full Xcode install and this builds with Command
Line Tools only. Don't "fix" it into a test target.
